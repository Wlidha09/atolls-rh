# Firebase migration validation

- `npm test`: **34 tests passed** against the native JSON repository and mocked conditional-write transport. Includes rollback, conflicting writes/retries, room booking races, scoped leave approvals, employee/Manager supervision, role protections and escalation checks, session revocation, inactive login security audits, external configured Dev sign-in, onboarding, monthly work-day math/report privacy, source conversion/import guards, and actual SMTP delivery to an isolated local SMTP server.
- REST transport tests generate an ephemeral RSA key and verify service-account OAuth assertions, ETag/If-Match headers, conditional conflict responses, sanitized errors, token caching, and signed realtime tokens bound to an employee and a specific session. No real credentials are saved.
- Firebase Realtime Database emulator **v4.11.2**: exercised real REST reads, normalization of Firebase JSON/null values, ETag conditional writes and conflicting meeting prevention.
- Published the included rules to the emulator. Verified active-session revision access; denied anonymous reads, private HR-data reads, direct employee/role/revision writes, wrong employee/session combinations, wrong UID, deactivated accounts and expired sessions. Emulator-only unsigned identity tokens were used for these rules tests; the production token issuer uses RS256-signed custom tokens.
- Production browser checks with isolated emulator fixtures and the real native service: actual Firebase revision SSE updated departments and Work Tickets within a 5-second check, a draft survived an incoming revision, deferred updates appeared after closing its modal, saving worked, Roles and the Manager checkbox remained functional, HR received a summary while an employee received personal totals, desktop/mobile layouts had no page overflow, and no JavaScript errors occurred.
- Browser authenticated API handlers were intercepted to route to the isolated native service; Firebase custom-token exchange was mocked, while the revision stream and rule checks used the actual database emulator. The actual unauthenticated Next.js portal and Work Tickets endpoints returned JSON 401.
- Next.js production build passed. No Firebase/Turso credentials were needed for ordinary builds. The constrained execution environment used an external temporary shim for unavailable process-memory metrics, excluded from the source archive.

- `npm audit --omit=dev`: zero reported vulnerabilities at verification time.

## Limits of these checks

No access was available to the user's Firebase, Turso, Google or Netlify accounts. The hosted migration, Firebase service-account IAM access, real Firebase Authentication custom-token exchange, actual Google OAuth sign-in, and the scheduled Netlify notification function must be verified after configuration. Migration conversion and atomic import were tested; a live Turso-to-Firebase transfer was not performed. No production latency or cost claim is made.

The repository intentionally uses one organization-wide conditional write for business consistency. It suits a modest internal portal; large histories/high write concurrency require partitioning rather than assuming that changing database products alone guarantees speed. The browser receives only revision markers from Firebase; all HR data remains behind the Next.js session/role checks. Work Tickets is a calendar estimate, not verified attendance.
